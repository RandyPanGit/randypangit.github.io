測試補強尚承科技2025–2026

把一個沒人敢改的外包專案，變成可以放心改的專案

情境
接手外包公司交付的高爾夫球場管理系統，全專案只有 70 幾隻測試。要加新功能，但沒有人知道改動會不會弄壞既有流程。
判斷
沒有停下來「先補完測試再開發」——那在商業上不可行。改成每動一塊功能就先把那塊的行為用測試釘住，讓補測試變成開發的副產品而不是額外成本。以 SpringBootTest 覆蓋整條請求路徑，比純單元測試更能守住這種業務邏輯彼此纏繞的系統。
結果
三個月內測試案例從 70 多個增加到 700 多個，最終累積超過 2000 個。重構與新功能可以直接進主幹，回歸測試不再依賴人工點擊。
併發控制尚承科技2025–2026

同一個時段被兩個人同時預約，該擋在哪一層

情境
App 開放線上預約後，同日同時段出現重複預約。這種衝突只在流量尖峰才會現形，靠應用層「先查再寫」擋不住。
判斷
資料庫層的鎖會把壓力集中在單一資料源，而這套系統同時要支援多球場與多節點部署。改用 Redis 分散式鎖，把互斥的粒度縮到「球場 + 日期 + 時段」，讓不同球場、不同時段的預約完全不互相阻塞。
結果
重複預約消失，且鎖的競爭範圍夠小，熱門球場不會拖慢其他球場的預約。
架構遷移昕力資訊2018–2022

Gateway 從 Zuul 換到 Spring Cloud Gateway，順便把權限收攏

情境
API 管理平台原本以 Zuul 做路由。Zuul 1 的同步阻塞模型在連線數上來後成為瓶頸，而權限檢查散落在各個下游服務裡，規則不一致。
判斷
藉遷移到 Spring Cloud Gateway 的機會，把權限檢查與限流一併收進 Gateway 的 Filter 層。這讓下游服務只需專心處理業務，授權規則有唯一的真相來源。
結果
路由、權限檢查、限流統一在同一層維護。同期建立 SonarQube 掃描與優化後的 Git Flow，讓三人團隊的交付節奏穩定下來。
